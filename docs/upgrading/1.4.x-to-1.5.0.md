# 10. 1.4.x -> 1.5.0 (the last manual upgrade)

*Sect. 10 of the upgrade guide, `../UPGRADING.md`: read its opening first, for `SRC`, `REPO`, `SCRATCH` and `CLI_DIR`. A bare "sect. N" here is that guide's sect. N, and its index names the file. `ADOPTING.md` is `../ADOPTING.md`, an index too.*

*The version is the maintainer's to set at release: if this release ships under another number, read it for `1.5.0` throughout.*

1.5.0 adds the viewer's one-click update (B65). **It is the last upgrade you do by hand:** from 1.5.0 on, on the maintainer's machine, the viewer shows a badge when a newer release is tagged, and one click installs it (sect. 11, `self-update.md`). What it brings:
- a `VERSION` file in the tool folder, the version your copy is at;
- the updater: `updater.py`, `updater_helper.py` and `schema_merge.py` in the tool folder, three API routes and a badge in the viewer;
- `x-project-owned` in `ticket.schema.json`: the JSON pointers whose values are yours (the id patterns and the `status`, `severity`, `owner_area` and `author` enums), so an update keeps them;
- `update_source` in `config.json`, the maintainer's `ticket-system/` folder on this machine (absent: updates are off);
- `.claude/tickets/README.md`, the agents README: what changed for agents, per release, plus `ACTION` lines for your copy. `tickets.py readme` writes the first one.

The schema and `config.json` structures change, so it's a minor (user rule, 2026-09-30: "Minor only updates when a configuration or json structure change happens"). **There is no data migration:** your tickets and `tags.json` stay as they are, and `update_source` is optional. Read `CHANGELOG.md` [1.5.0] first.

A copy on 1.4.0, 1.4.1 or 1.4.2 follows this section; a 1.4.0 copy also takes 1.4.1's changes here (read sect. 9, "What behaves differently"). A copy on 1.3.x does sect. 8 first, except its rules-doc step (sect. 8 step 5), then this section.

## What behaves differently

- **The viewer may show a badge, "Update x.y.z",** in its top bar, for a browser on this PC, when `update_source` is set and a newer release is tagged in it. A click shows the changelog and asks to confirm. See sect. 11 for what the update does and does not do.
- **The viewer accepts one POST:** `/api/update/apply`, only from this PC, with `Host` and `Origin` naming `127.0.0.1:<PORT>` or `localhost:<PORT>` and the page's token. Everything else is still GET only, and a LAN client never gets the token. `GET /api/update` and `GET /api/update/status` are new read routes.
- **`serve.py` may restore files at start.** If an update was cut off part-way (its helper process died), the next `serve.py` start puts the backup back before it serves, and says so in one `note:` line.
- **`tickets.py` may print one line to stderr** after an update: `tickets: store updated to x.y.z - see .claude/tickets/README.md`. It prints once per release (`build/tickets/readme-seen` records it).
- **`tickets.py readme`** is a new subcommand: it writes `.claude/tickets/README.md` when it is missing.
- **`schema_merge.py`** merges a release's schema with yours from the command line (step 6); the updater uses the same merge.

## Steps

1. **File the upgrade and set it `in_progress`** (sect. 3 step 1).
   **Check:** `list --active` shows it.
2. **Get 1.5.0** (sect. 3 step 2): `python <SRC>/tools/release.py export 1.5.0 <SCRATCH>/ts-1.5.0` on the maintainer's machine, or a clone brought to the release.
   **Check:** `PAYLOAD/../VERSION` reads `1.5.0`, and `PAYLOAD/src/tools/tickets/VERSION` reads `1.5.0` too.
3. **Back up** the tool folder, the schema, `config.json`, the rules doc and the skill (sect. 3 step 3).
   **Stop the viewer** (sect. 3 step 4).
   **Check:** `--stop` reports the viewer stopped, or nothing recorded.
4. **Copy the tool folder, except `icons/`** (sect. 3 step 5): everything in `PAYLOAD/src/tools/tickets/` except `icons/` over `REPO/<CLI_DIR>/`. New files: `VERSION`, `updater.py`, `updater_helper.py`, `schema_merge.py`. Changed since 1.4.2: `tickets.py`, `serve.py`, `app.js`, `index.html`, `style.css`. Never copy `icons/`.
   **Check:** `REPO/<CLI_DIR>/VERSION` reads `1.5.0`, and `git status` shows nothing under `icons/`.
5. **`.gitignore`:** make sure it holds `build/tickets/` (or `build/`; `ADOPTING.md` step 9). The updater keeps its work area, its backups and the staged skill, hooks and rules doc there, and none of it belongs in a commit.
   **Check:** `git check-ignore build/tickets/update/status.json` prints the path.
6. **Merge the schema.** The release's schema gains `x-project-owned`; your values at those pointers are kept, the rest is the release's. **The base is the schema of the release your copy runs now** (`<old>`: 1.4.2, 1.4.1 or 1.4.0, your skill's version row):
   ```bash
   python <SRC>/tools/release.py export <old> <SCRATCH>/ts-<old>
   python <CLI_DIR>/schema_merge.py PAYLOAD/dot-claude/tickets/ticket.schema.json .claude/tickets/ticket.schema.json --base <SCRATCH>/ts-<old>/payload/dot-claude/tickets/ticket.schema.json --out <SCRATCH>/ticket.schema.json
   ```
   - **Exit 0** prints `wrote ...`: diff `<SCRATCH>/ticket.schema.json` against yours (expect `x-project-owned` added and your enums and id patterns unchanged), then copy it over `.claude/tickets/ticket.schema.json`.
   - **Exit 2** prints a `PROBLEM` line per place your schema differs from `<old>`'s outside your values (for example a `maxLength` you changed). Nothing is written. Such a local edit is a fork the updater would refuse too: bring it back to the release's value, or tell the maintainer why you need it, then run the command again. A title or description you reworded is kept and is no problem.
   **Check:** `python <CLI_DIR>/tickets.py validate` prints `OK: ...`, and the installed schema's `x-project-owned` lists six pointers.
7. **`config.json`: `update_source`.** On the maintainer's machine, add the absolute path of the maintainer's `ticket-system/` folder, backslashes doubled in JSON:
   ```json
   "update_source": "C:\\path\\to\\source-repo\\ticket-system"
   ```
   Leave it out to keep updates off (a copy from a GitHub clone always does: the path must be on this machine, and the clone updates by hand). A value that is not a string stops `serve.py` with `ERROR .claude/tickets/config.json: update_source must be a string ...`.
   **Check:** `python <CLI_DIR>/tickets.py validate` still prints `OK: ...`.
8. **Merge the rules doc** with `release.py merge-doc`, as in sect. 9 step 5, with `--base` the rules doc of the release you run now. 1.5.0's doc gains `update_source` in its `config.json` table, the agents README and the updater's files in sect. 1, and the update badge and routes in sect. 4 and 6; expect a conflict wherever you rewrote those paragraphs.
   **Check:** as in sect. 9 step 5: no conflict marker line left, and a re-run with this release's doc as `--base` exits 0 with an identical file.
9. **The skill.** Take `PAYLOAD/dot-claude/skills/tickets/SKILL.md` whole (it gains "After an update": read the agents README when the CLI points there, and act on `ACTION` lines only as your role allows), put your Settings rows back, and set the version row to `1.5.0`. Have a separate read-only agent review it, and install it only after a pass.
   **Check:** the review passed.
10. **The hooks,** if you installed them: nothing changed in them.
11. **Write the agents README:** `python <CLI_DIR>/tickets.py readme`.
    **Check:** it prints `wrote .claude/tickets/README.md`, and the file holds a `## 1.5.0` section with the release's lines for agents (they come from `update_source`'s manifest; without `update_source` it says "nothing new").
12. **Start the viewer again** (`python -u <CLI_DIR>/serve.py --foreground` as a background task, with `--all-interfaces` only if the LAN must reach it).
    **Check:** `/api/health` answers with your marker, and `curl -s http://127.0.0.1:<PORT>/api/update` shows `"installed": "1.5.0"` and `"state": "current"` (with `update_source`) or `"off"` (without). `identify`: the `release 1.5.0` block shows every product file matching, the icons adapted, and the skill `settings-only`.
13. **Commit** the tool folder, the schema, `config.json`, `.gitignore`, the rules doc, the skill and `.claude/tickets/README.md`, in one commit.
    **Check:** `git status` shows nothing left of them, and nothing under `build/`.
14. **Tell the maintainer** you run 1.5.0, and close the upgrade ticket on that evidence, with `--link-commit <hash>`.

From here on, a new release is a click: sect. 11.
