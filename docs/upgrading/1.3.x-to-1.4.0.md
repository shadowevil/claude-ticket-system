# 8. 1.3.x -> 1.4.0

*Sect. 8 of the upgrade guide, `../UPGRADING.md`: read its opening first, for `SRC`, `REPO`, `SCRATCH` and `CLI_DIR`. A bare "sect. N" here is that guide's sect. N, and its index names the file. `ADOPTING.md` is `../ADOPTING.md`, an index too.*

1.4.0 adds typed ticket links, comments, two statuses, a new ticket detail view and a localhost viewer:
- a ticket may carry `links.blocks`, `links.blocked_by` and `links.relates_to`, and a `comments` list (CLI-only);
- the `status` enum gains `user_review` and `verified`;
- `config.json` may carry `page_title`;
- the viewer binds `127.0.0.1` by default, and `serve.py --all-interfaces` opts in to the LAN.

The schema and `config.json` structures change, so it's a minor release (user rule, 2026-09-30: "Minor only updates when a configuration or json structure change happens"). **There is no data migration:** every new field is optional, so your existing tickets, `tags.json` and `config.json` stay as they are and validate unchanged. Read `CHANGELOG.md` [1.4.0] first.

A copy on 1.3.0 or 1.3.1 follows this section. A copy on 1.2.x does sect. 7 first, with 1.4.0 in place of 1.3.0 where its step 2 says to take the release (read every per-release note after the one you run).

## What behaves differently

- **The viewer binds 127.0.0.1 by default.** Before 1.4.0 it bound `0.0.0.0`, so a phone or another machine on the LAN could reach it, and Windows could ask about the firewall at the first start.
  - **Anything that reaches your viewer over the LAN stops working after the restart** (a phone, another PC) until you start it with `python -u <CLI_DIR>/serve.py --foreground --all-interfaces`, or `serve.py --all-interfaces` for the detached form. That start may show the firewall prompt (choose Private networks only; never change firewall settings from a script or agent).
  - **The maintainer's master site keeps working** if it runs on the same PC as the viewer: it reaches viewers over 127.0.0.1 and needs no flag.
  - `--local-only` is still accepted and changes nothing: localhost is the default now. A start line that has it keeps working.
  - A viewer that is already running keeps its old binding until it is stopped: `serve.py --stop`, then start it again with the flag you want. A detached start with a different binding does not switch a running one.
- **Typed ticket links.** `links.blocks`, `links.blocked_by` and `links.relates_to` are optional lists of ticket ids.
  - The old `links.tickets` is still read, as relates-to. Nothing converts it.
  - `tickets.py new` and `set`, and `author.py draft` and `new`, take `--block`, `--blocked-by` and `--relates` (ids or bare numbers, comma-separated, repeatable). `set` also takes `--remove-block`, `--remove-blocked-by` and `--remove-relates`.
  - **A block is written on both tickets** by the one command (A `blocks` B is B `blocked_by` A), and both are written or neither. The other ticket must exist: `ERROR no such ticket: <id> (a block is written on both tickets)`.
  - `list` adds `[blocked by <ids>]` and `[N comment(s)]` after the summary.
- **Comments.** `tickets.py comment <id> --author <enum> --body-file <file|->` (and `author.py comment`, with `--json`) appends `{author, at, body}` to the ticket's `comments` and bumps `updated`. Comments are written by the CLI only; the viewer stays read-only. They are never edited.
- **Two new statuses** (B59, B60). Both count as active (`list --active`, the viewer's Active filter), and `done` still needs its commit link.
  - `verified` sits between `in_review` and `done`: the review passed and the checks are green, and only landing it (commit, merge, delivery) is left. The order is open, in_progress, in_review, user_review, verified, blocked, done, wont_do.
  - `user_review` means the ticket needs the user to look at it or decide. It can be set from any active status, and the viewer shows it as a filled amber pill, with its count highlighted while any ticket waits.
  - The CLI offers them only once your schema's `status` enum has them (step 4): until then `set --status verified` is a usage error, and your existing tickets validate unchanged.
- **`author.py --from-json` refuses `comments`.** Create the ticket, then add each comment with `comment`.
- **`new` with a block writes all or nothing.** The new ticket and the other side of each block are checked first; if one fails, no ticket is created and no other ticket changes.
- **Mentions.** A ticket id written in a body or a comment (outside code) is linked by the viewer, and the ticket's detail shows "Mentions" and "Mentioned by" groups. `show` prints `mentions:` and `mentioned by:` lines. Nothing is stored, so agents just write the id.
- **`validate`** gains these checks:
  - a typed link to a ticket that does not exist, or to the ticket itself, fails (as `links.tickets` did);
  - a block with one side only fails: `<id>: links.blocks names X, but X's links.blocked_by lacks <id>: run tickets.py set <id> --block X`;
  - a ticket that both blocks and is blocked by the same one fails;
  - a comment dated before its ticket was created, or in the future, fails;
  - **a warning, not a failure:** `<id>: mentions <ids> in its body or comments, which is not in the store`. Existing text that names an id with no ticket gives this warning; the exit code stays 0.
- **The detail view.** The viewer shows the subject, the tags, the body, the linked tickets (blocked by, blocks, relates to, mentions, mentioned by; each opens that ticket), then the comments, newest first, 10 at a time with a "load more" button.
- **`page_title`** (optional `config.json` key). It sets the page title and heading, used as written. Without it, or set to `""`, the title is `<store_name> Tickets`, as before.
- **Tag names and hyphens.** The name rule is unchanged: lowercase letters, digits and `_`. A hyphen is not allowed, so a tag for the `owner_area` value `re-docs` is written `re_docs`.
- **Old schemas refuse the new fields.** Your `ticket.schema.json`'s `links` and the ticket object do not allow the new keys until you merge the release's nodes (step 4). Until then `validate` still passes on your unchanged tickets, but a ticket with a typed link or a comment fails the schema.

## Steps

1. **File the upgrade and set it `in_progress`** (sect. 3 step 1).
   **Check:** `list --active` shows it.
2. **Get 1.4.0** (sect. 3 step 2): a clone brought to the release, or `python <SRC>/tools/release.py export 1.4.0 <SCRATCH>/ts-1.4.0` on the maintainer's machine.
   **Check:** `PAYLOAD/../VERSION` reads `1.4.0`.
3. **Back up** the tool folder, the schema, the rules doc and the skill (sect. 3 step 3). The tickets are not touched.
   **Stop the viewer** (sect. 3 step 4).
   **Check:** `--stop` reports the viewer stopped, or nothing recorded.
4. **Copy in the new files and merge the schema.**
   - Copy these six from `PAYLOAD/src/tools/tickets/` into `REPO/<CLI_DIR>/`: `tickets.py`, `author.py`, `serve.py`, `app.js`, `index.html` and `style.css`. Copying everything except `icons/` works too (sect. 3 step 5). Never copy `icons/`: yours are baked per project, and `lib/`, `manifest.webmanifest` and `make_icons.py` are unchanged.
   - **The schema.** Keep your enums, except `status`: add `user_review` and `verified`, so `properties.status.enum` becomes `["open", "in_progress", "in_review", "user_review", "verified", "blocked", "done", "wont_do"]` (plus any status of your own). In `ticket.schema.json`, take from the release: the `properties.links` node (its `tickets` item now `$ref`s `#/$defs/ticket_ids`, and `blocks`, `blocked_by` and `relates_to` are new), the new top-level `properties.comments` node, the new `$defs.ticket_ids`, and the changed top `description`.
   **Check:** `python <CLI_DIR>/tickets.py set --help` offers `user_review` and `verified` under `--status`, and `python <CLI_DIR>/tickets.py validate` prints `OK: T tickets valid against the schema, tags and links`, plus `WARNING ... mentions ...` lines only where a body names an id that has no ticket.
5. **The rules doc and the skill.**
   - Your rules doc keeps your project text and section numbers. Take these from `PAYLOAD/dot-claude/docs/tickets.md`: sect. 1, the `page_title` key; sect. 2, the `status` row, the link rows and the `comments` row; sect. 3, the `verified` / `user_review` examples, the `--active` list, the typed-links, comments and mentions bullets, the changed `validate` bullet, the hyphen sentence in the tag-store paragraph, and the `author.py` additions; sect. 4, the start commands, the port bullet, the firewall bullet and the page bullet; sect. 5, the "status tracks the work", `user_review` and "close with evidence" rules; sect. 7.
   - Take `PAYLOAD/dot-claude/skills/tickets/SKILL.md` whole, put your Settings rows back (the Viewer row now says it binds 127.0.0.1), and set the version row to `1.4.0`.
   - Have a separate read-only agent review the skill, and install it only after a pass.
   **Check:** the review passed, and `grep -n "comment" .claude/docs/tickets.md` finds the new bullets.
6. **Set `page_title`** in `config.json` only if you want a title other than `<store_name> Tickets` (optional).
   **Check:** `tickets.py --help` still prints your store's line (a bad value prints `ERROR .claude/tickets/config.json: page_title must be a string, ...`).
7. **Start the viewer again** (`python -u <CLI_DIR>/serve.py --foreground` as a background task; add `--all-interfaces` if the LAN must reach it, see "What behaves differently"). `serve.py` changed, so a viewer still running from before the copy must be restarted.
   **Check:**
   - the start line says `bound to 127.0.0.1` (or `0.0.0.0` with the flag);
   - `/api/tickets` returns your tickets with an empty `problems`;
   - the page shows the new detail view (links, then comments), and your title;
   - `identify`: the `release 1.4.0` block shows every product file matching, the icons adapted, and the skill `settings-only`.
8. **Try it once (optional).** On a scratch copy, or a ticket you may touch: `set <id> --blocked-by <other>`, then `show <other>` lists the block, `comment <id> --author <you> --body-file -`, and `validate` stays `OK`. The commands change tickets, so do not run them on a ticket you cannot change.
9. **The hooks,** if you installed them: copy in `hooklib/ticket_store.py` (T2 now also ties on a `verified` ticket; `user_review` does not tie), with `rules/write/t2_ticket_system_fork.py` (its self-test cases) and `RULES.md`, by sect. 6, "Upgrading installed hooks": stage, run the staged self-test with `--scratch`, have it reviewed, install, run the self-test again.
   **Check:** the installed self-test ends in `0 failure(s)`.
10. **Commit** the tool files, the schema, the rules doc, the skill and any hook files you copied (and `config.json` if you set `page_title`), in one commit.
    **Check:** `git status` shows nothing left of them.
11. **Tell the maintainer** you run 1.4.0, and close the upgrade ticket on that evidence.
