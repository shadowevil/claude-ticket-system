# 7. 1.2.x -> 1.3.0

*Assessed 2026-10-21 (B47, under the documentation standard): kept whole. One upgrade procedure, followed in full on a 1.2.x copy; its steps cite each other and "What behaves differently", and code cites its step 7 by number.*

*Sect. 7 of the upgrade guide, `../UPGRADING.md`: read its opening first, for `SRC`, `REPO`, `SCRATCH` and `CLI_DIR`. A bare "sect. N" here is that guide's sect. N, and its index names the file. `ADOPTING.md` is `../ADOPTING.md`, an index too.*

1.3.0 numbers the tags:
- `tags.json` becomes a numbered tag store, and tickets hold tag ids instead of names.
- `config.json` may carry `tag_groups`: the tags every ticket must carry.
- `author.py`, a new tool beside `tickets.py`, is how agents author tickets, and it moves your store across.

Several JSON structures change (`tags.json`, the schema's `tags`, `config.json` and the viewer API), so it's a minor release (user rule, 2026-09-30: "Minor only updates when a configuration or json structure change happens"). Read `CHANGELOG.md` [1.3.0] first.

A copy on 1.1.0 or 1.0.0 does sect. 4 and 5 first. A copy on 1.2.0 or 1.2.1 comes straight here, and also takes the 1.2.1 and 1.2.2 per-release notes (the `.gitignore` line, the hooks).

## What behaves differently

- **Tags are ids on disk.**
  - `tags.json` is `{"format": 2, "next_id": <n>, "tags": {"<id>": {"name", "color", "description"}}}`. Ids are never reused or renumbered.
  - A ticket's `tags` is a list of ids, such as `[1, 4]`.
  - You still type names. `--tags`, `--add-tag`, `--remove-tag`, `list --tag`, `author.py` and `import` records take names or ids. `list`, `show`, `validate` and the viewer print names.
  - `author.py tags rename` changes a tag's name in the store only; no ticket changes. It waits until the tickets are converted (below).
- **A tag name needs a letter or `_`.** An all-digit name reads as an id, so the probe refuses one (step 7).
- **Until the probe, readers take the old store, and writers refuse.**
  - `list`, `show`, `validate` and the viewer read the old `tags.json` and tickets that hold tag names.
  - They don't resolve an integer or an all-digit tag value while the store is unnumbered. 1.2's tools never wrote an integer, and an all-digit name like `2024` reads as an id from 1.3.0 on. `validate` fails each one with the same line the probe gives: `tag id N on a ticket while tags.json is not numbered yet; replace it with the tag's name (the ticket system's docs/UPGRADING.md sect. 7 step 7)`, or `the tag name 'N' is all digits, which reads as a tag id; rename it by hand first (the ticket system's docs/UPGRADING.md sect. 7 step 7)`. (A 1.3.0 `tickets.py` names the guide as `Ticket Master's docs/UPGRADING.md`; it is the same step.) `list` and `show` print the raw value, and the viewer shows it as a grey chip. Step 7 says how to fix them.
  - Every writer (`new`, `set`, `import`, `author.py`) refuses with `ERROR tags.json is in the old format (a name -> colour map); every writer refuses until it is numbered: run author.py tags --probe, then try again`.
- **From the probe until the conversion, readers take both forms.** Writers write ids, and a `set` on a ticket that still holds names writes them as ids. `validate` warns and still passes: `WARNING N tickets still carry tag names: run author.py --convert-all`.
  - `author.py tags rename` refuses in this window, writing nothing (`ERROR rename refused, nothing written`), while any ticket still carries the old name as text, since that ticket would lose the tag. It also refuses while an unconverted ticket carries the new name as text that `tags.json` lacks, since that ticket would gain the tag. And it refuses while any ticket file doesn't read, since that file can't be checked: `ERROR rename refused, nothing written: N ticket file(s) do not read, ...` (`validate` names them). Rename after step 8.
- **Tag groups** (optional, `config.json` `tag_groups`). `new`, `set`, `import` and `author.py new` refuse a ticket that breaks a group, and `validate` fails it (step 10).
- **The tag-store lock.** `author.py tags add`, `tags rename`, `tags --probe` and a real `--convert` or `--convert-all` (not a `--dry-run`) hold `.claude/tickets/tags.json.lock` while they read and write, so two writers take turns.
  - A writer that waits 30 s for it refuses: `ERROR tags.json is locked: <path> (pid N at <UTC time>, S s old) was not released within 30 s. ...`, with `tags.json` unchanged.
  - Nothing breaks a lock automatically. If no `tickets.py` or `author.py` is running, one was killed while it held the lock: delete that file and try again.
  - The file exists only while a command runs. Keep it out of git (step 13).
- **`set` and `show` on a broken ticket.**
  - `set` refuses up front only a ticket it can't work on: `ERROR <id> cannot be changed with set: <problem>; fix the file, then run validate`. That covers a file holding another id, `tags` that isn't a list, `links` that isn't an object, a `links` entry that isn't a list, and a body that isn't text when you pass `--append-body-file`.
  - Otherwise `set` applies the change and checks the whole result: `ERROR refusing to write an invalid ticket:` and the problems. So `set` can repair a ticket, such as a summary that is too long or a missing `tags` list or body.
  - `show` prints a ticket that is a JSON object but invalid, then `WARNING <id> is invalid (N problem(s); the first: ...); run validate`. A file that isn't a JSON object gives `ERROR <id>: not a JSON object but ...; run validate, then fix the file`.
- **Stricter reads.** A file holding `NaN` or `Infinity` (a ticket, `tags.json`, `config.json`, an `import` file, `--from-json`) is refused as not valid JSON. So is a file nested too deeply to read. A missing or unreadable input file gives one `ERROR` line naming it, not a traceback. A ticket read while Windows reports the file busy is tried again.
- **The viewer.**
  - `/api/tickets` gives `tags` keyed by id (`{"1": {"name", "color", "description"}}`), plus `tag_format` and `tag_groups`.
  - The page shows the same names and colours. A tag value the store doesn't hold is a grey, dashed chip titled "Not in tags.json". So is every id while the store is still in the old format.
  - Its problems box lists each `tags.json` entry that doesn't read, such as `tags.json: tag 9 ('ui'): needs a #rrggbb color`, and that tag's chips are grey. From 1.3.1, `validate` reports each ticket carrying such a tag as `<file>: tag id N: its entry in tags.json is invalid (the tags.json problem for tag N says why)` or `<file>: tag '<name>': its entry in tags.json is invalid (...)`, and a tag group naming it as `config.json tag_groups[i] ('<g>'): tag(s) "<a>", "<b>" have an invalid entry in tags.json (...)`, not as an unknown tag. A store that doesn't read at all shows `tags.json: <reason>`. Until the probe has run, the box also lists `tags.json is in the old format: run author.py tags --probe`.
- **The schema's `tags` items** are an id (an integer, 1 or more) or a name. `tickets.py` checks the items itself, whatever your schema says, so an older schema keeps working.
- **No abbreviated options.** `tickets.py`, `author.py` and `serve.py` take only full option names, so `--body` for `--body-file` or `--sto` for `--stop` is now an `unrecognized arguments` error. Check your own scripts for one.
- **`set` never writes into a ticket in place** (B45). When Windows keeps refusing the move (another process holds the file open, such as an editor), `set` fails with `ERROR could not write <id>.json (moving the new version over it was refused: ...); the ticket is unchanged; another process may hold the file open: close it, then run set again` and removes its temporary file. 1.2.2 wrote into the file instead, which could leave it cut off.
- **`import --abort-interrupted`** (B42, B45) refuses while the import it would clean up is running. It checks the journal's structure (contiguous ids matching its `first`, `last`, `count` and pid, the store's prefix, sane length): a journal that fails removes no ticket. A ticket older than the journal is kept. This catches a cut-off or carelessly edited journal; it does not stop a deliberately consistent forgery. It touches only the names the tool writes, and also removes the `<id>.new-<pid>.tmp` or `<id>.set-<pid>.tmp` that a killed `new` or `set` left, once that process is gone. From 1.3.1: a tag store write (`author.py tags ...`) killed part-way leaves `tags.store-<pid>.tmp` beside `tags.json`, which is unchanged. `tickets.py import --abort-interrupted` removes it once that process is gone, and keeps and names one whose process still runs. The killed write also leaves `tags.json.lock`: delete it by hand once no `tickets.py` or `author.py` is running, as the lock refusal says. With nothing to clean: `ERROR no interrupted import, no killed new or set and no killed tag store write: ...` (1.3.0: `ERROR no interrupted import and no killed new or set: ...`).
- **The viewer ignores `.tmp` files** (B46): a leftover no longer causes a page refresh.
- **Ticket numbers have at most 9 digits** (more only when `first_ticket_number` needs it). A file named like a ticket with a longer number is not read as a ticket by `list`, `show`, `set`, `new` or the viewer, and `validate` fails it: `FAIL XY-<N digits>.json: not a ticket file name, ...: rename or remove it`.
- **A full store refuses.** When the next id would have more digits than the limit (9, or one more than `first_ticket_number` has), `new`, `import` and `author.py new` fail with `ERROR the store is full: ...; nothing was written`.
  - A batch that would run past the limit refuses with `ERROR the batch does not fit: ... Only the first <K> record(s) fit ...: import at most <K>; nothing was written`.
  - A full store caused by a killed import's journal points at `--abort-interrupted`: the `ERROR` says the highest id is claimed by an interrupted import's journal, and that `tickets.py import --abort-interrupted` frees its ids once no import is running.
- **`--abort-interrupted` says what each pid is, and a way out.** Its refusal while an import seems to run gives every pid a note on what it is: `pid N is python.exe`, `pid N is PING.EXE, not python, so most likely not the import` (the program's name, on Windows), or `pid N could not be checked (access refused)`. It then gives a by-hand way out with that pid's file patterns (`journal.import-<pid>.tmp` and `<PREFIX>[0-9]*.import-<pid>.tmp`, such as `XY-[0-9]*.import-<pid>.tmp`, and the files found; for a running `new` or `set`, `<PREFIX>[0-9]*.new-<pid>.tmp` and `<PREFIX>[0-9]*.set-<pid>.tmp`). If a pid is not a python process running `tickets.py`, or you are sure no import is running, delete those files by hand, then run `validate`. The patterns are for bash or PowerShell (`Remove-Item -Path '<folder>\XY-[0-9]*.import-<pid>.tmp'`); cmd's `del` does not understand `[0-9]`.
- **The optional hooks changed** (B45, B46): `hooklib/fixtures.py`, `paths.py`, `prompt_clock.py`, `output.py`, `selftest.py` and `ticket_store.py`, `rules/write/t2_ticket_system_fork.py`, and `RULES.md`. The self-test's `--scratch` refuses the project root and `.claude/` itself (`self-test: refused: the --scratch folder <dir> is a project root, ...` or `... is a .claude folder itself, ...`); pass `.claude/scratch/<role>/<task>/`. A live hook call run inside a release export no longer writes `payload/build/hooks/tickets/` there. Upgrade the hooks as in sect. 6.

## Steps

1. **File the upgrade and set it `in_progress`** (sect. 3 step 1).
   **Check:** `list --active` shows it.
2. **Get 1.3.0 or a later 1.3.x** (sect. 3 step 2): `release.py export 1.3.1 <SCRATCH>/ts-1.3.1` on the maintainer's machine, or a clone, which holds the latest release. A later 1.3.x goes through these same steps; read its per-release note too, and wherever a step below says `1.3.0`, use the version you install.
   **Check:** `PAYLOAD/../VERSION` reads `1.3.0` or a later 1.3.x.
3. **Back up** the tool folder, the schema, the rules doc, the skill and **the whole `.claude/tickets/` folder**. The move rewrites `tags.json` and every ticket that carries a tag.
   - For a large store, rehearse steps 5 to 9 first, on a copy of `REPO/<CLI_DIR>/` and `REPO/.claude/tickets/` in `<SCRATCH>` at the same relative paths. The tool works on the store above it, so your real one is untouched (`ADOPTING.md`, "Migrating from another tracker", step 3).

   **Check:** your backup lists the tickets folder.
4. **Stop the viewer** (sect. 3 step 4). No other session files a ticket from step 5 until step 7 is done, because every writer refuses in between.
   **Check:** `--stop` reports the viewer stopped, or nothing recorded.
5. **Copy in the new files.** Copy these five from `PAYLOAD/src/tools/tickets/` into `REPO/<CLI_DIR>/`: `tickets.py`, `author.py` (new), `serve.py`, `app.js` and `style.css`. They are the only tool files changed since 1.2.0, so your icons and `lib/` stay as they are. Copying everything except `icons/` works too (sect. 3 step 5), and needs no re-bake. Don't copy `icons/`: the release's say `XY`.
   **Check:** `python <CLI_DIR>/tickets.py validate` prints `WARNING tags.json is in the old format ...` and, if any ticket has a tag, `WARNING N tickets still carry tag names ...`. The only new `FAIL` lines it may print are these, and step 7 fixes each one:
   - `FAIL <file>: unknown tag '<name>' (not in tags.json: ...)`: a name on a ticket that `tags.json` lacks. The probe adds it.
   - `FAIL tags.json: the tag name 'N' is all digits, which reads as a tag id; rename it by hand first, in tags.json and on every ticket carrying it (the ticket system's docs/UPGRADING.md sect. 7 step 7)` and `FAIL <file>: the tag name 'N' is all digits, which reads as a tag id; rename it by hand first (the ticket system's docs/UPGRADING.md sect. 7 step 7)`.
   - `FAIL <file>: tag id N on a ticket while tags.json is not numbered yet; replace it with the tag's name (the ticket system's docs/UPGRADING.md sect. 7 step 7)`: an integer put on a ticket by hand.
6. **The schema.** Your `ticket.schema.json` keeps your enums. Replace its `properties.tags` node with the release's: items are `anyOf` an integer of at least 1, or a name.
   **Check:** `validate` reports as in step 5.
7. **Number the tag store.**

   <!-- tickets.py and author.py cite "the ticket system's docs/UPGRADING.md sect. 7 step 7" in their all-digit and tag-id messages: keep the hand rename at this number, or change the code with it. -->

   **First, rename any all-digit tag name, and replace any integer tag value.** Do it before the probe, which refuses both and writes nothing. 1.2 has no rename command, so edit the files by hand, UTF-8 with LF. Each ticket keeps its `updated`, since this is a format fix, not an edit. For a tag named `2024`:
   1. Find the files. Step 5's `FAIL ... all digits` lines name exactly the tickets that carry it as a tag, plus `tags.json`. `grep -l '"2024"' .claude/tickets/*.json` helps, but it also finds a ticket whose other fields hold exactly `"2024"`, such as `target_patch`; a tags list spans several lines, so grep can't narrow it to the list.
   2. In `tags.json`, rename the key: `"2024": {...}` becomes `"y2024": {...}`. Choose a new name with at least one letter or `_` that `tags.json` doesn't already have.
   3. In each ticket that `validate` named, replace `"2024"` with `"y2024"` in its `tags` list only. Leave every other field as it is.
   4. For a `tag id N on a ticket ...` line, replace the integer in that ticket's `tags` with the tag's name.

   **Check:** `python <CLI_DIR>/tickets.py validate` shows none of step 5's all-digit or `tag id` lines.

   Then save the usage counts. `author.py tags` reads the old store, with provisional ids in name order:
   ```bash
   python <CLI_DIR>/author.py tags > <SCRATCH>/tags-before.txt
   python <CLI_DIR>/author.py tags --probe --dry-run
   python <CLI_DIR>/author.py tags --probe
   ```
   The dry run writes nothing. It prints:
   - `tags.json: would number the N tag(s) of the old format in name order, ids 1..N`. Every name, colour and description is kept.
   - `would add tag <id> <name> (on K ticket(s))` for each name on a ticket that `tags.json` lacks. The probe gives it the next id, the colour `#808080` and the description `found by probe`. Afterwards, give it a real colour and description in `tags.json` by hand, keeping its id and name.
   - `WARNING <file>: ...` for a ticket file that doesn't read or has no tags list. Its tags are not probed; `validate` names it.
   - **A refusal:** `FAIL` lines, then `ERROR tags.json has N problem(s); fix them first, nothing written` or `ERROR probe refused, nothing written: N value(s) cannot be loaded`. An all-digit name, an integer value or an invalid tag name can't be loaded. Fix it as described at the start of this step, then repeat the dry run.
   - `ERROR tags.json is locked: ...`: another `author.py` holds the lock (see "What behaves differently").

   The probe itself prints the same lines without "would", then `wrote tags.json: N tag(s), next_id M`.
   **Check:** a second `tags --probe` prints `nothing to add: tags.json is numbered and holds every tag name on the tickets`. Writers work again from here.
8. **Convert the tickets:**
   ```bash
   python <CLI_DIR>/author.py --convert-all --dry-run
   python <CLI_DIR>/author.py --convert-all
   ```
   - The dry run prints one line per ticket that would change, such as `XY-0002.json: docs, ui, core -> 4, 5, 3`, then `dry run: would convert N of T ticket(s) (V tag value(s)); nothing written`.
   - The real run writes each ticket atomically through `tickets.py`'s writer. It leaves ids alone and keeps `updated` as it was, since this is a format change, not an edit. The tag groups aren't checked here; step 10 covers them. It prints `converted N of T ticket(s) (V tag value(s)); K needed no change`.
   - A name the store lacks stops it before anything is written: `FAIL <file>: unknown tag '<name>' (run author.py tags --probe first)`, then `ERROR nothing converted: N problem(s)`. Run step 7 again, then this step.
   - If it stops part-way, for example on a file another process holds, it prints `ERROR stopped after converting N of M ticket(s); the rest are unchanged: run it again`.
   - `--convert <file or id>` converts one ticket.

   **Check:** a second `--convert-all` prints `converted 0 of T ticket(s) (0 tag value(s)); T needed no change`.
9. **Validate:** `python <CLI_DIR>/tickets.py validate`.
   **Check:** it prints `OK: T tickets valid against the schema, tags and links`, with no `WARNING` line. Then compare `author.py tags` with `<SCRATCH>/tags-before.txt`: every tag there has the same name and ticket count now, so no ticket lost a tag.
10. **Tag groups (optional).** Add `tag_groups` to `config.json`; `ADOPTING.md` step 6 gives the format. Then:
    - `python <CLI_DIR>/author.py rules` prints each group as a rule, such as `type: pick exactly 1 of bug, cleanup, docs`.
    - `validate` fails each ticket that already breaks a group, closed ones included: `FAIL XY-0004.json: tag group type: pick exactly 1 of bug, cleanup, docs (has none)`.
    - **Such a ticket can't change at all, not even its status, until its tags satisfy the group.** `set` refuses with `ERROR refusing to write an invalid ticket:` and the group's line. Fix the tags in the same call as the change you want: `set 4 --status in_progress --add-tag cleanup`.
    - Add a group when you are ready to fix the tickets `validate` lists, or start it at `"min": 0`.

    **Check:** `validate` prints `OK: ...`.
11. **The rules doc and the skill.**
    - Your rules doc keeps your project text and section numbers. Take these from `PAYLOAD/dot-claude/docs/tickets.md`:
      - sect. 1: the `tags.json`, `tags.json.lock` and `author.py` rows, and the `tag_groups` key;

      - sect. 3: "Tags, tag groups and `author.py`", and the `set`, `show`, `validate` and body-file bullets;
