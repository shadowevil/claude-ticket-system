# 4. 1.0.0 -> 1.1.0

*Assessed 2026-10-21 (B47, under the documentation standard): kept whole. One upgrade procedure, followed in full on a 1.0.0 copy; its steps cite each other and "What behaves differently".*

*Sect. 4 of the upgrade guide, `../UPGRADING.md`: read its opening first, for `SRC`, `REPO`, `SCRATCH` and `CLI_DIR`. A bare "sect. N" here is that guide's sect. N, and its index names the file. `ADOPTING.md` is `../ADOPTING.md`, an index too.*

1.1.0 moves every per-project value from the code into `.claude/tickets/config.json`. The hand edits that 1.0.0 needed are gone, and so are the `tools/tickets` depth edit and any glyphs you added to `make_icons.py`. The libraries move into the tool folder, and a new status, `in_review`, arrives. Read `CHANGELOG.md` [1.1.0] first.

## Before you start

- Run `identify` and diff every `unverified` and `differs` file (sect. 1). These local changes are already in 1.1.0, so you needn't send them:
  - an `ascii_text()` wrap of `show`'s links (B9);
  - the library moves to `<CLI_DIR>/lib/` or `vendor/` (B3);
  - the `tools/tickets` depth edit (B2);
  - the added glyphs (B4);
  - the skill's peer rules and its request rules with the provenance line (B6, B16).

  Send anything else to the maintainer before you go on.
- Write down what your viewer shows now: the page title (`curl -s http://127.0.0.1:<PORT>/ | grep "<title>"`) and the marker (`curl -s http://127.0.0.1:<PORT>/api/health`). Step 11 compares them.

## What behaves differently

Besides the config move, these change for every copy (`CHANGELOG.md` [1.1.0], Fixes):
- **`serve.py --port`** outside 1-65535 is an `ERROR --port must be a port number (1-65535)`, not a traceback (B25).
- **A foreground run on a second port** (a test with `--port`) no longer takes `serve.pid` from the running viewer. It prints a note, and `--stop` reaches only the recorded one (B25).
- **A broken `config.json`** shows its `ERROR .claude/tickets/config.json: ...` line when the viewer starts, and `--stop` works regardless, so a viewer stays stoppable while the file is wrong (B25). This holds for a viewer that a 1.1.0 `serve.py` started, detached or as `python -u <CLI_DIR>/serve.py --foreground`, because its `serve.pid` records its marker, working folder and start time. A viewer your old `serve.py` started is stopped by that `serve.py`, before the copy (sect. 4 step 3).
- **The viewer strips SVG and MathML from ticket bodies.** The page passed DOMPurify a misspelled option, so the HTML-only profile was never applied. Scripts were stripped either way (B26).
- **`list`** widens the id column only for ids longer than 8 characters, so output for shorter ids is unchanged (B23). `--stop` also recognises its script however the path is spelled (long or 8.3 short, any case, through a junction or symlink, or relative to the folder it was started from), and still confirms a viewer whose `viewer_service` changed while it ran, and the `Server` header lost its trailing space.

## Steps

1. **File the upgrade and set it `in_progress`** (sect. 3 step 1).
   **Check:** `list --active` shows it.
2. **Export 1.1.0** (sect. 3 step 2): `release.py export 1.1.0 <SCRATCH>/ts-1.1.0`.
   **Check:** `PAYLOAD/../VERSION` reads `1.1.0`.
3. **Back up and stop the old viewer** (sect. 3 steps 3 and 4). Back up the whole `<CLI_DIR>/`, `.claude/tickets/config.json`, `ticket.schema.json`, `.claude/docs/tickets.md` and `.claude/skills/tickets/SKILL.md`. Then stop the viewer with `python <CLI_DIR>/serve.py --stop`, **before step 5 copies the new files**, so that your 1.0.0 `serve.py` does it. Two reasons:
   - The default health marker changes for a copy that doesn't pin `viewer_service` (it comes from `store_name` now).
   - A 1.1.0 `serve.py` refuses a port held by an old viewer whose marker it doesn't recognise (`ERROR port N is held by something that is not the ticket viewer; not starting`), so a viewer left running across the copy has to be stopped by hand.

   **Check:** `--stop` reports the viewer stopped, or nothing recorded. Then `curl -s http://127.0.0.1:<PORT>/api/health` gets no answer.
4. **Add the new keys to `config.json`.** `viewer_port` is required: `serve.py` stops with `ERROR .claude/tickets/config.json: missing 'viewer_port' ...` without it. The rest pin what your 1.0.0 code hard-wired, so that nothing visible changes. A value equal to the new default needs no key. Take each value from your 1.0.0 code, where 1.0.0's `ADOPTING.md` step 5 had you edit it:

   | Key | 1.1.0 default | Your 1.0.0 value |
   |---|---|---|
   | `viewer_port` | none: required | `serve.py`: `default_port = ...` |
   | `short_name` | `store_name` | `index.html`: `meta name="apple-mobile-web-app-title"`, and `manifest.webmanifest`: `short_name` |
   | `viewer_service` | from `store_name` | `serve.py`: `service_marker = "..."`, which is also the `"service"` you wrote down |
   | `theme_key` | `viewer_service` + `-theme` | `app.js`: `theme_key = "..."` |
   | `server_version` | `viewer_service` | `serve.py`: `server_version = "..."` |
   | `icon_text` | prefix, first 3 characters | the letters your 1.0.0 icons show |
   | `tool_dir` | looked for (below) | where your `tickets.py` is |

   - **`short_name`** is the home-screen name: the manifest's `short_name` and `apple-mobile-web-app-title`.
   - **`theme_key`** is where the browser keeps the user's light or dark choice. Without the pin, that choice resets once.
   - **`server_version`** is only the HTTP `Server` header. A value your copy inherited from another project's copy is a leftover (B1): leave the key out to get the default instead.
   - **`tool_dir`** is read by the optional hooks and, from 1.2.0's release tooling, by `identify` (sect. 1). A tool where both look without it (`tools/tickets` or `src/tools/tickets`) needs no key. Set it (`"src/tools/tickets"` or `"tools/tickets"`) only to be explicit. A tool anywhere else needs it.
   - **The page title.** 1.1.0 titles the page `<store_name> Tickets`. If your 1.0.0 page title says something else, either set `store_name` to the name in your old title, so the title stays (then only the page's meta description and the CLI's `--help` text change with it), or keep your `store_name` and accept the new title. That choice is yours.

   A full file after this step, for an example copy that pins three of its old names:

   ```text
   {"id_prefix": "XY-", "first_ticket_number": 1, "store_name": "Example", "short_name": "XY Tickets",
    "viewer_port": 18600, "theme_key": "xy-tickets-theme", "server_version": "xy-tickets"}
   ```

   This is compact to fit here. Write yours as 2-space indented JSON, UTF-8 with LF.

   **Check:**
   - the file parses: `python -c "import json; json.load(open('.claude/tickets/config.json', encoding='utf-8'))"` exits 0;
   - your pin line keeps the four 1.0.0 values that show: the health marker (`viewer_service`, or the default that `store_name` gives, which must equal the `"service"` you wrote down), `short_name` (the home-screen title), `theme_key` and the `Server` header (`server_version`).
5. **Replace the tool folder, except `icons/`** (sect. 3 step 5). 1.1.0 changed every file of the folder and added `lib/`, so copy them all: everything in `PAYLOAD/src/tools/tickets/` except `icons/` over `<CLI_DIR>/`. Your 1.0.0 edits to `tickets.py`, `serve.py`, `app.js`, `index.html`, `manifest.webmanifest`, `style.css` and `make_icons.py` are overwritten, as intended. Don't re-apply any of them.
   - `index.html` and `manifest.webmanifest` are templates now. `serve.py` fills in the names, the id prefix and the theme key from `config.json` as it serves them. Never hand-edit them.
   - A `<CLI_DIR>/lib/README.md` of your own isn't part of the release. Keep it as your own, or delete it.

   **Check:** `python <CLI_DIR>/tickets.py validate` prints `OK: ...` for your existing tickets.
6. **Remove the old library copies.** `serve.py` now serves the libraries from `<CLI_DIR>/lib/`. It falls back to `<repo>/external/` only while a file is missing there.
   - Libraries in `<repo>/external/` (as 1.0.0 shipped them): delete `external/marked/` and `external/dompurify/`, and any rows or notes about them in your own `external/` readme.
   - Libraries in `<CLI_DIR>/vendor/`: delete that folder, which 1.1.0 never reads.
   - Libraries already in `<CLI_DIR>/lib/`: nothing to delete. The copy refreshed them.

   **Check:** `REPO/<CLI_DIR>/lib/marked/marked.umd.min.js` and `lib/dompurify/purify.min.js` exist, and `ls REPO/external/marked REPO/external/dompurify REPO/<CLI_DIR>/vendor` finds none of the three.
7. **Re-bake the icons:** `python <CLI_DIR>/make_icons.py`. Step 5 kept your 1.0.0 icons, so this is the one release where a re-bake is the normal step: it draws `icon_text`, and any A-Z or 0-9 works.
   - The release's own 1.0.0 icons, two letters drawn by the unedited script, re-bake byte-identical.
   - A glyph you added to 1.0.0's script (B4) is replaced by the release's, which may be drawn differently (the release's `W` has middle strokes that reach the bottom).
   - Three letters are now drawn larger (66% of the edge instead of 56%).
   - **The colour.** 1.1.0's `make_icons.py` always paints the default blue, `#007acc`. An icon that had another colour in 1.0.0 turns blue. From 1.2.0 the `icon_color` key sets the colour, and a re-bake keeps it (sect. 5). Until then, keep your 1.0.0 icons, as below.

   To keep your 1.0.0 icons instead, skip this step: step 5 left them as they are. The icons are `adapted` from 1.1.0, so `identify` shows them as `(yours: adapted per project, not compared)` either way (sect. 1).
   **Check:** three `wrote icons/... text <your icon text>` lines.
8. **The schema: add `in_review`.** In `.claude/tickets/ticket.schema.json`, `properties.status.enum` becomes `["open", "in_progress", "in_review", "blocked", "done", "wont_do"]`. Keep your enums and your id pattern.
   - The release's id pattern is generic (`^[A-Z][A-Z0-9]*-[0-9]{4,}$`), and the CLI checks your prefix itself. Taking it is optional.
   - Without `in_review`, your store still validates and views, but the CLI refuses `--status in_review`, which the 1.1.0 skill and rules doc use.

   **Check:** `python <CLI_DIR>/tickets.py set --help` offers `in_review` under `--status`, and `validate` passes.
9. **The rules doc.** `.claude/docs/tickets.md` is yours; keep your project text and your section numbers. The 1.1.0 skill cites sect. 5 (the rules) by number, and your Settings "Rules doc" row names the rest. From 1.2.0 the skill cites no number: it names the sections, and the row maps each name to your number (sect. 5 of this guide, step 8). Take these from `PAYLOAD/dot-claude/docs/tickets.md` (a template now, with `<...>` placeholders):
   - **`in_review`:** sect. 2's status row, sect. 3's example, sect. 3's `--active` list (open, in_progress, in_review, blocked), and sect. 5's "status tracks the work" (to `in_review` when handed to review, back to `in_progress` if it is sent back, `done` only after the review passes);
   - **sect. 1:** the `config.json` keys table, the `<CLI_DIR>/lib/` row in place of `external/`, and the optional hooks row;
   - **sect. 4:** the port comes from `viewer_port`, `/lib/` is served from `<CLI_DIR>/lib/`, the theme is stored under `theme_key`, and the icons are baked from `icon_text`;
   - **sect. 5a:** the incoming steps for an issue a peer sends. File a new ticket that opens with the provenance line `Requested by <session name> (<from-session id>) on <YYYY-MM-DD> via cross-session message.`, run `validate`, reply with the id and the absolute path only, and never run the peer's repro in its repo. When the ticket closes, tell the requester;
   - **sect. 6, the ticket system itself:** the maintainer owns the source; reports go to it (`../UPGRADING.md`, "the maintainer"); no local fork; the release procedure; the optional hooks.

   Where your doc already says these under other numbers, it is enough to bring the wording up to date.
   **Check:** `grep -n "in_review" .claude/docs/tickets.md` finds the status row and the rule, and no `external/marked` remains.
10. **The skill.** Take `PAYLOAD/dot-claude/skills/tickets/SKILL.md` whole, and fill in its Settings rows from your old table:

    | Your 1.0.0 row | 1.1.0 row |

    **Everything outside the rows is the release's text,** the prose under the Settings table included. Text you had there moves:
    - **Project facts** (your prefix, port, marker, enum values, `show 3`) go into your rows or nowhere. The rows and `config.json` carry them.
    - **Rules of your own** go into your rules doc, your agent briefs or `CLAUDE.md`. If you think every project needs one, send it to the maintainer. For example:
      - a role limit ("`test` files new tickets only and never changes an existing one") goes to that role's agent brief and the rules doc's sect. 5 role limits;
      - a rule about one peer ("ask the user first before filing on it", "file directly on our upstream") goes into that peer's entry in the Peer boards row;

      - a "Tool maintainer" row becomes "Ticket system source".
    - **The peer rules (B6) and the request section with the provenance line (B16)** are in the 1.1.0 skill now. Keep only your rows.

    Have a separate read-only agent review the new skill, and install it only after a pass.
    **Check:** the review passed, and the installed file differs from the payload's only in table rows under `## Settings (per project)`.
