# 9. 1.4.0 -> 1.4.1

*Sect. 9 of the upgrade guide, `../UPGRADING.md`: read its opening first, for `SRC`, `REPO`, `SCRATCH` and `CLI_DIR`. A bare "sect. N" here is that guide's sect. N, and its index names the file. `ADOPTING.md` is `../ADOPTING.md`, an index too.*

*The version is the maintainer's to set at release: if this release ships under another number, read it for `1.4.1` throughout.*

1.4.1 makes the rules doc merge one command, enforces the commit link on `done`, and quiets `identify`:
- `release.py merge-doc` merges the release's rules doc into yours, keeping your values and your lines (B61);
- `tickets.py` and `author.py` refuse status `done` without a commit link (B62);
- `release.py identify` prints the per-file lines only for the closest release (B63).

No configuration or JSON structure changes, so it's a patch (user rule, 2026-09-30: "Patch should be for smaller changes like UI updates and such"). **There is no data migration:** your tickets, `tags.json`, `config.json` and schema stay as they are. Read `CHANGELOG.md` [1.4.1] first.

A copy on 1.4.0 follows this section. A copy on 1.3.x does sect. 8 first (with this release in place of 1.4.0 where its step 2 says to take the release), then the steps here from step 4.

## What behaves differently

- **`done` needs a commit link.** `tickets.py new --status done` and `set <id> --status done`, and `author.py draft` and `new` (flags or `--from-json`), refuse it while the ticket's `links.commits` is empty and the same command adds none:
  `ERROR status done needs a commit link (links.commits is empty): add --link-commit <hash> to the same command`.
  - Close with `set <id> --status done --link-commit <hash>`, as the rules doc and the skill already said. A ticket that already holds a commit link can be set `done` without repeating it.
  - `wont_do` needs no commit, as before.
  - **Old stores still validate.** A done ticket closed before this release with no commit link is not changed and does not fail `validate`; `validate` prints one `WARNING N done ticket(s) have no commit link (<ids>): ...` line and exits 0. `import` still takes such records, and `set` on such a ticket still works as long as it does not set `--status done` again.
- **`identify` is shorter.** Every release still gets its summary line; the per-file lines are printed only under the closest release, followed by `(N per-file line(s) of other releases not shown; --verbose shows every release's)`. `--verbose` prints them all, with the exact matches.
- **The rules-doc template carries markers.** Three kinds of line are new in `PAYLOAD/dot-claude/docs/tickets.md`, all HTML comments the rendered page does not show:
  - `<!-- template:begin -->` / `<!-- template:end -->` around the porting note. Delete the note with its markers when you port by hand; `merge-doc` drops it.
  - `<!-- project:begin rules -->` / `<!-- project:end rules -->`, an empty pair at the end of sect. 5. Put your project's own rules between them, and any other lines of yours anywhere in a pair with a name of your own: `merge-doc` keeps them.
  - The free-text placeholders are capitals (`<AREAS>`, `<AUTHORS>`, `<NEIGHBOURS: ...>`, `<ROLE_LIMITS: ...>`, `<DESIGN_DOC: ...>`, `<PEER>`): the line holding one is yours, and `merge-doc` keeps your text there. `<NEIGHBOURS: ...>` (sect. 4, the port bullet) and `<DESIGN_DOC: ...>` (sect. 5) now sit on lines of their own, so release changes around them still merge.
  - A doc ported from an earlier template has none of these and still merges: `merge-doc` aligns it with the release text, and with `--base` it reads the old free-text wording ("Say here what else ...", `<where design reasoning goes>`, `<Add any role limits ...>`) to move your text to the new lines.

## Steps

1. **File the upgrade and set it `in_progress`** (sect. 3 step 1).
   **Check:** `list --active` shows it.
2. **Get 1.4.1** (sect. 3 step 2): a clone brought to the release, or `python <SRC>/tools/release.py export 1.4.1 <SCRATCH>/ts-1.4.1` on the maintainer's machine.
   **Check:** `PAYLOAD/../VERSION` reads `1.4.1`.
3. **Back up** the tool folder, the rules doc and the skill (sect. 3 step 3). The tickets, the schema and `config.json` are not touched.
   **Stop the viewer** (sect. 3 step 4).
   **Check:** `--stop` reports the viewer stopped, or nothing recorded.
4. **Copy in the new files:** `tickets.py` and `author.py` from `PAYLOAD/src/tools/tickets/` into `REPO/<CLI_DIR>/`. Copying everything except `icons/` works too (sect. 3 step 5). Never copy `icons/`.
   **Check:** `python <CLI_DIR>/tickets.py validate` prints `OK: ...`, plus at most one `WARNING ... done ticket(s) have no commit link ...` line (and any `mentions` warnings you had).
5. **Merge the rules doc** with one command, against the 1.4.0 doc as the base (sect. 3 step 7):
   ```bash
   python <SRC>/tools/release.py export 1.4.0 <SCRATCH>/ts-1.4.0
   python <SRC>/tools/release.py merge-doc PAYLOAD/dot-claude/docs/tickets.md <REPO>/.claude/docs/tickets.md --base <SCRATCH>/ts-1.4.0/payload/dot-claude/docs/tickets.md --out <SCRATCH>/tickets.md
   ```
   `<SRC>/tools/release.py` must be this release's (a clone at 1.4.1, or the export's `tools/release.py`). With a clone, `git -C <SRC> show tickets-v1.4.0:payload/dot-claude/docs/tickets.md` gives the base. `--out` must be a new file: the command refuses to overwrite an input. It prints the values it used and where each came from, then `NOTE` and `LOOK` lines.
   - **Exit 0** means no text of yours was dropped: every line of your doc is in the merged doc, or is 1.4.0's own wording of a line 1.4.1 changed.
   - **Exit 2** means a LOOK. Each LOOK project line is **not** in the merged doc: put it back where it belongs in `<SCRATCH>/tickets.md`, inside a `<!-- project:begin <name> -->` / `<!-- project:end <name> -->` pair so the next merge keeps it, or let it go if the release now says the same. A LOOK value with no source: run it again with `--set NAME=value` (for example `--set SCRATCH=.claude/scratch/<role>/<task>`).
   - Diff `<SCRATCH>/tickets.md` against your doc. From a 1.4.0 port whose release lines you left alone, expect only the release's changes:
     - the "close with evidence" rule and the `validate` bullet (B62);
     - the port bullet split so your "keeps clear of" sentence has its own line;
     - the design-doc rule ending in `The design doc:` with your doc's path on its own line;
     - the empty `rules` pair at the end of sect. 5.
   - Then copy the file over `<REPO>/.claude/docs/tickets.md`.
   **Check:** the diff shows only the release's changes and the lines you placed, and `merge-doc` run again on the result (with `--base` this release's doc, `PAYLOAD/dot-claude/docs/tickets.md`, and `--out` another scratch file) exits 0 with no `LOOK` line.
6. **The skill.** Take `PAYLOAD/dot-claude/skills/tickets/SKILL.md` whole (only its Close wording changed), put your Settings rows back, and set the version row to `1.4.1`. Have a separate read-only agent review it, and install it only after a pass.
   **Check:** the review passed.
7. **Start the viewer again** (`python -u <CLI_DIR>/serve.py --foreground` as a background task, with `--all-interfaces` only if the LAN must reach it). `serve.py` did not change, but `tickets.py`, which it reads the store with, did.
   **Check:** `/api/tickets` returns your tickets with an empty `problems`; `identify`: the `release 1.4.1` block shows every product file matching, the icons adapted, and the skill `settings-only`, and no other release's per-file lines.
8. **The hooks,** if you installed them: nothing changed in them.
9. **Commit** the two tool files, the rules doc and the skill, in one commit.
   **Check:** `git status` shows nothing left of them.
10. **Tell the maintainer** you run 1.4.1, and close the upgrade ticket on that evidence, with `--link-commit <hash>`: `done` now needs it.
